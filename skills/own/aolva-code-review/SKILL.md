# Aolva Code Review

系统化代码审查方法。审查目的:在**功能性、安全性、可维护性、性能**四个维度找真实问题,并按严重度排序交付。

## 审查顺序(按风险从高到低)

1. **安全**:注入(SQL/命令/路径)、敏感信息泄漏(硬编码密钥、日志打点)、越权/鉴权缺失、不可信输入校验、依赖漏洞。
2. **正确性**:空指针/边界/类型、并发与竞态、错误处理(吞异常、失败路径)、状态一致性。
3. **性能**:明显 O(n²)、循环内 IO/网络、无界增长、资源泄漏(连接/文件句柄)。
4. **可维护性**:重复代码、命名、复杂度、注释与文档、测试覆盖盲区。
5. **契约**:与调用方/接口文档不一致、破坏性变更未标注。

## 输出格式

```text
## 结论
[需修改才能合并] | [建议修改] | [可合并,有建议]

## 问题清单
- [严重][安全] 位置:描述;利用方式;修复建议
- [中][正确性] 位置:描述;最小复现思路;修复建议
- [低][可维护性] 位置:描述;建议

## 亮点(值得保留的做法)
```

## 方法规则

- **先读全貌再下结论**:先看文件结构、调用链,再逐行;禁止只凭片段断言。
- **可执行优先**:每个问题给出"改什么、怎么改"的最小可落地建议;不空谈风格。
- **验证**:能本地复现的 bug 给出复现命令;修复建议给出可编译/可测试的写法。
- **严重度判定**:能导致数据丢失/安全事件/生产故障 = 严重;影响特定输入 = 中;纯风格 = 低。
- **语言与规模适配**:按语言惯例审查(Go 的 error、Python 的异常、TS 的类型),不套跨语言模板。

## 边界

- 审查只做分析,不直接改代码(除非用户明确要求"审查并修复")。
- 拿不准的问题标注"需确认",不臆断。
