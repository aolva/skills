# Aolva Release Ops

平台各产品(web/api/ios/desktop)共用发布纪律。目标:**每次发布可解释、可回滚、可追溯**。

## 发布前检查单

1. **范围与版本**:确认本次发布内容清单;语义化版本号(bugfix/feature/breaking 对应 minor/patch/major)。
2. **验证状态**:CI 全绿;相关测试通过;涉及数据迁移时迁移脚本已在 staging 跑过。
3. **变更记录**:CHANGELOG 已更新(按用户/开发双视角);破坏性变更已标注。
4. **回滚预案**:确认上次稳定版本号与回滚路径(镜像/构建产物可获取);涉及数据库迁移的发布,确认迁移可逆或已备份。
5. **发布窗口**:是否需避开高峰;是否需要灰度(先小比例验证再全量)。

## 执行顺序

1. 环境顺序:staging → 灰度(可选)→ production;每步验证通过才进下一步。
2. 灰度:默认小比例(如 5%)+ 观察窗口(≥15 分钟)+ 指标(错误率/延迟/核心功能探针)。
3. 全量后:冒烟验证关键路径(登录/核心流程),检查告警与日志无异常。

## 回滚触发条件

- 错误率显著上升、核心功能不可用、数据完整性受损 —— 立即回滚,不纠结修复。
- 回滚动作:切回上一稳定版本(或反做迁移);记录回滚原因与时间。
- 回滚后:保留现场证据(日志/指标截图)供复盘;不急着重新发布,先定位根因。

## 规则

- **发布即文档**:每次发布留痕(时间/版本/内容/验证/操作人),统一记录。
- **不静默发布**:生产变更需用户知晓;深夜自动发布等特殊安排先说明。
- **数据库变更**:先备份/评估可逆性;DDL 破坏性操作(删列/改类型)分步执行。
- **凭据**:部署密钥走 CI secret,不落本地文件、不进提交。

## 交付

发布报告:范围 → 验证 → 灰度/全量时间线 → 冒烟结果 → 回滚预案状态。
